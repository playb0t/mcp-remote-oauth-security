# Five mcp-remote CVE records, five CISA scores, no stated fix

*Alex Gercog · AI systems engineer and security researcher*

Published on LinkedIn on 8 October 2026 as the second edition of the article of 30 September 2026 (mirrored in [article-2026-09-30.md](article-2026-09-30.md)). This file carries the text as published, with one line adapted for this copy (the closing contact line). The records and advisories it discusses are in this repository.

On 6 October CISA scored the last of the five CVE records that MITRE published for mcp-remote on 24 September. The scores now read 9.8 and 9.1 Critical, 8.8, 7.5 and 7.5 High. In npm's per-version counter for the last seven days, 204,636 of the package's 714,492 downloads were versions those records list. No maintainer has stated a fix.

A note first. LinkedIn removed the previous version of this article, citing its inclusion of IP addresses. This version focuses on the findings and defensive takeaways. The full technical analysis, evidence and disclosure timeline are available on playb0t.com and GitHub; both links are at the end.

## What the package does

mcp-remote is the npm bridge that lets local MCP clients such as Claude Desktop and Cursor reach remote MCP servers over OAuth. Vendors put it in their setup pages. Developers paste the line into a config and forget it. Between my private report on 17 February and the records on 24 September, npm counted 17,862,832 downloads of it.

The flaw is simple to state. When a client connects to a remote server that wants OAuth, the server answers with a challenge that carries an address, the place where its resource metadata lives. The client fetches it. The metadata names an authorization server, and the client fetches that too. If an answer is a redirect, the client follows. Every one of those addresses came from the other side of the connection, and in the versions I reviewed the client treated each as a place it was allowed to go.

That is the odd thing about OAuth discovery. The protocol exists so a client can work out whom to trust, and the first thing the client does is trust whoever answered.

A client with no destination policy will fetch a loopback address, a machine on the office network or the cloud provider's metadata service as readily as anything on the public internet. My canaries on my own machine confirmed the requests for two of the findings. I contacted no external service and published no weaponized code.

## The five records

MITRE wrote the descriptions and published the records as the CVE Numbering Authority. CISA attached the scores in its role as an authorized data publisher. NVD lists all five as Deferred and shows CISA's numbers, so those are the official scores, and I accept both as they stand. Beside each record I name the kind of evidence my advisory rests on, because a reproduced request and a hardening finding are not the same thing. Each advisory states its evidence class in its own text.

CVE-2026-51996, 9.8 Critical. MITRE: arbitrary code execution through getServerUrlHash, versions 0.1.16 through 0.1.38. Behind it, advisory F-04, a hardening record on the MD5-derived storage namespace.

CVE-2026-51994, 9.1 Critical. MITRE: SSRF through the resource_metadata URL taken from the server's WWW-Authenticate header, 0.1.32 through 0.1.38. Behind it, F-01, reproduced with a canary.

CVE-2026-51997, 8.8 High. MITRE: arbitrary code execution through the open() functions, 0.1.16 through 0.1.38. Behind it, F-08, a source review of the internal-address check that runs before the browser is launched.

CVE-2026-51995, 7.5 High. MITRE: sensitive-information disclosure through the authorization-server-metadata and utils components, 0.1.32 through 0.1.38. Behind it, F-02, blind SSRF through a server-selected authorization server, reproduced with a canary.

CVE-2026-52001, 7.5 High, scored on 6 October. MITRE: sensitive-information disclosure through the SSE transport fetch wrapper, 0.1.18 through 0.1.38. Behind it, F-11, token-origin binding at the SSE wrapper, a hardening record.

The package had a Critical record before. JFrog's CVE-2025-6514, a command injection through the authorization endpoint that JFrog scored 9.6, was fixed in 0.1.16. The five records above begin at 0.1.16, 0.1.18 and 0.1.32.

## Why your scanner is quiet

As of today the GitHub Advisory Database carries the five records as unreviewed entries with no package attached. Dependabot alerts on reviewed, package-mapped advisories, so a team that relies on it gets nothing for these. It can have a listed version pinned in its lockfile, run its usual checks and see a clean report. OSV goes the other way and lists 0.1.38 as fixed. The commit it names as the fix is the 0.1.38 release itself. 0.1.38 is the version I reviewed, and the records include it.

From the maintainer, still no statement of a fix. The repository changed owners after my report, and the current release, 0.14.3, dates from 21 September. Whether it closes each finding has not been established in any source I track, and I have not done it myself.

One layer down, the picture is better. In late September the official MCP SDKs published advisories on the same boundary in their repositories. The TypeScript SDK's record, CVE-2026-104850, covers an OAuth client sending its credentials to an authorization server the MCP server chose; the fix binds credentials to the expected issuer and shipped in SDK 1.31.0 and client package 2.2.0. Other researchers found those flaws and reported them there, as they should. But mcp-remote bundles the SDK into its own release. The version I reviewed pins SDK 1.25.3 and the current one carries client 2.0.0, both inside that advisory's affected ranges.

The server side of the same class is now on the record too. In early October the independent researcher Syed Anas Mohiuddin published a four-month update on what he calls protocol pivoting. MCP servers at Google, JPMorgan Chase, Weaviate, France's DINUM and the city of Tangerang in Indonesia fetched addresses that arrived as tool arguments and did not check where they led. Google's record, CVE-2026-14540, scored 8.0 and fixed in the pull request the record cites, is the one with a number; the others carry merged fixes or advisories. His material does not mention mcp-remote, and the code is different. The class is the same, a request to an address the other side supplied, with the address arriving from the opposite direction. He opened the server side. These five records are the client side.

## What a client has to enforce

An address the other side handed you stays data until the client decides to trust it with a request, and at that point the client should be able to say which rule it applied. Four controls cover the common part.

A destination policy before every discovery request. Permit the expected schemes, resolve the name, then reject loopback, link-local, private, multicast and reserved destinations. Run the policy after DNS resolution, because a hostname can point anywhere.

The same policy on every redirect hop. If the check runs only on the first URL, one redirect is enough to skip it. Handle redirects yourself, keep a small redirect budget, and classify every destination before the next request.

Credentials at rest in the operating system's secret store, because file permissions limit other users and do nothing against same-user tooling, sync, backup or a copy of the profile. mcp-remote's own README says it stores all credential information in a directory under the user's home folder.

At the transport, bind each token to its issuer, audience, resource and destination origin, and strip credentials before any cross-origin request.

## The check you can run today

Search your MCP client configs, package.json files and lockfiles for mcp-remote pinned anywhere from 0.1.16 to 0.1.38, the versions the records list. If your own setup page sends users through mcp-remote, offer a direct connection where the client supports one, and pin a version instead of latest. If you ship a client of your own, find every fetch whose URL arrived in a server response and ask three things. What stops it from reaching an internal address? Does that check run after DNS resolution? Does it run again on every redirect? If the answer to the first question is "nothing", you have the same class of problem, whichever client you use.
