# The Server Named the URL, the Client Went: Five mcp-remote CVE Records

*Alex Gercog · AI systems engineer and security researcher*

Published on LinkedIn on 30 September 2026. This file carries the article text as published, with one line adapted for this copy (the closing contact line). The records and advisories it discusses are in this repository.

mcp-remote was downloaded 1,170,325 times in the week of 21 to 27 September 2026. On 24 September MITRE published five CVE records for it. CISA has scored four: 9.8, 9.1, 8.8 and 7.5.

## The mechanism

When an MCP client connects to a remote server that wants OAuth, the server answers with a 401 and a WWW-Authenticate header. That header carries a URL, the place where the resource metadata lives. The client fetches it. The metadata then names an authorization server, and the client fetches that too. If either answer is a redirect, the client follows.

Every one of those addresses came from the other side of the connection. In the versions of mcp-remote I reviewed, the client treated each one as a place it was allowed to go.

That's the odd thing about OAuth discovery. The protocol exists so a client can work out whom to trust, and the first thing the client does is trust whoever answered.

## Who runs this code

mcp-remote is the npm bridge that lets local MCP clients such as Claude Desktop, Cursor and Windsurf reach remote MCP servers over OAuth. The download figure above is npm's own statistic for that week. I reviewed release 0.1.38; the seven findings trace back through earlier releases, one of them as far as 0.0.11.

A client that fetches a server-chosen address with no destination policy will fetch 127.0.0.1, an address on the office network or a cloud metadata endpoint as readily as anything on the public internet. My localhost canaries confirmed the requests for two of the findings. I contacted no external service and no real cloud endpoint, and I published no weaponized code.

The package has been here before. In July 2025 JFrog, as the CNA of record, published CVE-2025-6514, a 9.6 Critical command injection through the OAuth authorization endpoint, fixed in 0.1.16. That fix closed one path from server-supplied metadata into the operating system. The records below start at 0.1.16: the client still opened the server-named address in the browser without an internal-address check, and from 0.1.32 it also fetched whatever address the server named.

## The five records

On 24 September 2026, MITRE, acting as the CVE Numbering Authority, published five records that reference my advisories. CISA has since assessed four of them. The records follow as they stand on 29 September, ordered by CISA score. For each I give MITRE's description, condensed, and then the advisory behind it. Where the two version ranges differ, the record's comes first. If you don't need the per-record detail, skip to the scanner section.

How to read the scores. They are CISA's, attached to the records in its role as an authorized data publisher; MITRE wrote the descriptions and assigned no score. NVD lists all five as Deferred and shows CISA's numbers as secondary metrics; it holds none of its own, so CISA's are the official scores. The descriptions and the scores are the authorities' assessment of these findings, and I accept them as they stand; each advisory beside a record says what I did and which evidence it rests on.

CVE-2026-51996. MITRE: a remote attacker can execute arbitrary code via getServerUrlHash, 0.1.16 through 0.1.38. CISA, added on 29 September: 9.8 Critical, CWE-328, the weakness class advisory F-04 itself names; SSVC exploitation none, automatable yes, technical impact total. Behind it: advisory F-04, the MD5-derived storage namespace, a hardening record; the construction is present from 0.0.14 to 0.1.38.

CVE-2026-51994. MITRE: SSRF via the resource_metadata URL taken from a remote MCP server's WWW-Authenticate header, versions 0.1.32 through 0.1.38. CISA: 9.1 Critical, CWE-918. Behind it: advisory F-01, reproduced with a localhost canary, 0.1.32 to 0.1.38.

CVE-2026-51997. MITRE: a remote attacker can execute arbitrary code via the open() functions, 0.1.16 through 0.1.38. CISA: 8.8 High, user interaction required; CWE-20, CWE-94, CWE-918. Behind it: advisory F-08, a source review of the internal-address validation before the browser is launched, a gap the 0.1.16 fix for CVE-2025-6514 left open, 0.1.16 to 0.1.38.

CVE-2026-51995. MITRE: a remote attacker can obtain sensitive information via the authorization-server metadata components, 0.1.32 through 0.1.38. CISA: 7.5 High, CWE-200. Behind it: advisory F-02, blind SSRF through a server-selected authorization server origin, reproduced with a localhost canary, 0.1.32 to 0.1.38.

CVE-2026-52001. MITRE: a remote attacker can obtain sensitive information via the SSE transport fetch wrapper, 0.1.18 through 0.1.38. No CISA score. Behind it: advisory F-11, token-origin binding at the SSE wrapper, a hardening record; the construction is present from 0.0.18 to 0.1.38.

Two identifiers MITRE reserved for this request, CVE-2026-51998 and CVE-2026-51999, remain unpublished.

The remaining two advisories, F-09 and F-10, have no record (the F-numbers are stable research identifiers, so the numbering has gaps). F-09: OAuth tokens, client secrets and PKCE material stored as cleartext files under ~/.mcp-auth, from 0.0.11, with restrictive file permissions added in 0.1.37. F-10: discovery requests following redirects with no per-hop destination check, 0.1.32 to 0.1.38. Both rest on source review.

## What your scanner sees

As of 29 September the GitHub Advisory Database has one reviewed advisory mapped to the npm package mcp-remote, CVE-2025-6514 from July 2025; the five new records are there only as unreviewed entries with no package mapping, which Dependabot does not alert on. If your tooling relies on the reviewed, package-mapped advisories and not the CVE records, it hasn't seen these five yet. If it reads OSV instead, it will find 0.1.38 listed as fixed for these records. That version is inside the affected range, and the fix commit OSV names is the 0.1.38 release itself.

3 May. Clean-clone reverification after no maintainer response and no new release. F-02 promoted from source review to canary-verified. F-08 through F-11 first documented that day.

18 May. The 90-day window elapsed.

31 July. The public research package, v1.0.0, and the same day v1.0.1. The corrective release removed every severity number I had proposed, replaced one package-wide version range with a per-finding range, and reclassified F-04 and F-11 as hardening records. From that day, severity was the CNA's to assign.

24 September. Five records published.

29 September. CISA adds the 9.8.

The numbers that stand are the authorities'. The ones I deleted were mine. I'd rather publish with no score and let a CNA and CISA assess the records than carry a number my own vectors didn't compute.

## Where the package is now

The repository moved after my report was filed: github.com/geelen/mcp-remote now resolves to github.com/punkpeye/mcp-remote, under a new maintainer, and the OAuth path was reworked from late August through September. The current npm release is 0.14.3, published 21 September. The records describe 0.1.16 through 0.1.38; whether the current release closes each finding is not established, and the README still describes credentials stored under ~/.mcp-auth.

## What a client has to enforce

An address the other side handed you stays data until the client decides to trust it with a request, and at that point the client should be able to say which rule it applied. The advisories carry the remediation at the level I can state publicly, and the common part comes down to four controls.

An outbound-destination policy before every discovery request. Permit the expected schemes. Resolve the name, then reject loopback, link-local, private, multicast and reserved destinations. Bind discovery to the expected resource origin unless the protocol explicitly authorizes another. Run the policy after DNS resolution, because a hostname can point anywhere.

The same policy on every redirect hop. Handle redirects manually, classify each destination before the next request, keep a small redirect budget, and stop when the origin or the address class breaks policy. A check that runs on the first URL and never again is a check an attacker can route around with one 302.

Credentials at rest in the operating system's secret store. Where a file fallback cannot be avoided, authenticated encryption with the key kept outside the directory. File permissions limit other users; they do nothing against same-user tooling, sync, backup or a forensic copy of the profile. And at the transport, bind each token to its issuer, audience, resource and destination origin, and strip credentials before any cross-origin request.

## The check you can run today

If you ship or run anything that connects to remote MCP servers, four checks:

1. Find every fetch whose URL arrived in a server response: resource metadata, authorization-server metadata, redirect targets.
2. What stops that fetch from reaching 127.0.0.1, 10.0.0.0/8, 192.168.0.0/16, 169.254.169.254 or a link-local address, and does the check run after DNS resolution?
3. Does the same check run on every redirect hop, or on the first URL alone?
4. Where do long-lived OAuth tokens sit at rest, and who on the machine can read that directory?

If the answer to the second check is "nothing", you have the same class of problem, whichever client you use.
